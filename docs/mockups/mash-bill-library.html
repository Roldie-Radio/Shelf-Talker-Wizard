Mash Bill Library

Today, Bourbon Shelf Talkers lets staff build a mash bill one grain+percent chip at a time, but nothing about it is remembered — the same bottle gets re-researched and re-typed every time a new talker is made for it. This mockup proposes a small persistent library behind that chip UI: research a mash bill once (by hand, or auto-filled from Distiller.com the same way Nose/Palate/Finish already are), save it, and have it suggested automatically the next time that product comes up — on any register, via the same Server PC sync exportSync.js already uses for the WinePOS file.

The toggle below switches between the two ways a saved entry could be matched back to a talker — exact expression vs. distillery default — using Four Roses (one distillery, ten different recipe codes) to show why the choice matters.

Design notes

Exact Expression match

Library is keyed by the full product title. "Four Roses Single Barrel" and "Four Roses Small Batch" are separate entries, each with its own researched composition.

Trade-off: precise, but every new expression needs its own entry before recall works — no benefit until it's been saved once.

Distillery Default match

Library falls back to a per-distillery "typical" recipe when no exact entry exists. Fewer entries to maintain, and something is always suggested.

Trade-off: silently wrong for distilleries that run multiple recipes (Four Roses' ten recipe codes are the extreme case, but plenty of others blend by batch too). Needs a visible caution, never a silent fill.

Recommendation

Exact-expression as the primary match, with distillery-default as an opt-in fallback only when no exact entry exists — shown with the caution styling above, never auto-applied. That keeps the common case (a bottle staff has made a talker for before) fast and correct, while still offering something for a brand-new expression instead of a blank field.

Storage & sync

Lives in the same local data.db (better-sqlite3) as Print History — a new mash_bills table, not a separate file.

Cross-register sync reuses exportSync.js's shape (Server PC serves, others poll every ~30s) with one real addition: today that sync is one-directional (WinePOS → Server PC → everyone else) because only WinePOS ever writes the export. A mash bill can be researched at any register, so a non-Server PC needs a small write path too — it POSTs a new/edited entry to the Server PC's existing read-only port, which persists it and becomes the source every PC re-polls. Same single-writer-of-record shape as today, just with more than one PC allowed to propose a write.

Research: manual + Distiller.com

Reuses the exact pattern Find Tasting Notes already established: click, wait, get an editable preview before anything is committed — never a blind auto-fill. Same "scraper unconfirmed against the live site, double-check" caution the README already gives Nose/Palate/Finish.

Manual entry (today's chip UI) stays as-is and remains the fallback when Distiller.com has nothing.
