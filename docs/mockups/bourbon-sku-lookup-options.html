Bourbon Library SKU Lookup

Right now Store SKU only exists on the Edit Talker form for Beer (#beerFields in index.html) — Wine/Spirits and Bourbon talkers have no SKU field at all. Meanwhile every Bourbon Library entry has carried its own sku since a past release, but nothing on the talker form reads it: staff have to open the Library, find the SKU by eye, then type it somewhere else by hand. And the recall banner that already autofills Mash Bill/Nose/Palate/Finish (findMashBillMatch in app.js) only ever matches on an exact Product Title, never on SKU. Three ways to close that gap, below — all three reuse mashBillLibraryCache and the existing Use/Use All actions, they just differ in where staff trigger the match from.

Option:
Edit Talker · Product Type: Bourbon

Beer-only today (see #beerFields). Showing it for Bourbon too is what gives the recall match a second key to check besides title.

Mash Bill (optional)

Same chips, same field, same "Save this mash bill to the Mash Bill Library" checkbox below it — untouched.

How it works

  1. Add a Store SKU field to Bourbon talkers (today it's Beer-only).
  2. findMashBillMatch(title) becomes findMashBillMatch({ title, sku }) — checks SKU first, falls back to the existing exact-title match.
  3. Same #mashBillRecallBanner, same Use/Use All buttons, same "hidden, never deleted" behavior. Zero new endpoints, zero new UI components.
  4. Product Title gets filled in as part of "Use All" too, same as the other fields — a SKU match doesn't already know the title the way a title match trivially does.
SmallBuild effort
HighCode reuse
PassiveDiscoverability

Best when staff already know the SKU and are filling the form top-to-bottom anyway — it just quietly does the right thing as they type.

Edit Talker · Product Type: Bourbon

Opens a searchable list of every Library entry, by name or SKU — no need to already know the exact title.

Mash Bill (optional)

Search Bourbon Library

How it works

  1. A new button next to Product Title opens a picker over the same mashBillLibraryCache the Manage dialog already lists from.
  2. Its search box filters by name or SKU (renderMashBillLibraryList's filter gains one more field to check).
  3. Picking a row fills Product Title, Store SKU, Mash Bill, and Nose/Palate/Finish all at once — picking is the autofill action, no separate "Use All" click needed.
MediumBuild effort
MediumCode reuse
ExplicitDiscoverability

Best when staff aren't sure of the exact title or SKU and want to browse/search for it, the same way they'd search the Manage dialog today.

How it works

  1. A 4th pill joins Search by Name / SKU Lookup / Scan UPC, each already its own .method-panel in index.html.
  2. Its panel looks up the typed SKU against mashBillLibraryCache instead of the WinePOS export, and shows a confirm card — same pattern as the existing "Pick the Right Beer"/Confirm Untappd Match popups.
  3. "Use This Match" jumps to Edit Talker pre-filled, same as the other three methods already do.
Medium–LargeBuild effort
LowCode reuse
HighDiscoverability

Best when SKU-driven lookup should feel exactly like the existing SKU Lookup flow staff already use daily — at the cost of being the most new, separate code path of the three.

Comparing all three

OptionEffortReuses existing codeDiscoverabilityBest when…
A · Extend the recall banner Small High — same banner component, one new match key Passive — only shows up once staff type a SKU You already know the SKU and are filling the form top-to-bottom anyway
B · Pick from Bourbon Library Medium Medium — reuses the Manage dialog's list, new picker chrome Explicit — a visible button invites the action You're not sure of the exact title or SKU and want to browse/search
C · New Search-tab method Medium–Large Low — a new, mostly separate lookup path High — sits right next to the 3 lookup methods staff already use SKU-driven lookup should feel identical to the existing SKU Lookup flow

None of these are mutually exclusive — B is really just a nicer front door onto the same match logic A adds, and either could ship first with the other layered on later. C is the odd one out: it's the most discoverable, but the only one that doesn't build on top of the other two.
